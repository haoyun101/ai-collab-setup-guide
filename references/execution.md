# references · 执行卡、回执、命名、验收

> 触发：要出执行卡、要给文件起名、要验收本轮结果时。
> 主文件 `SKILL.md`，本文件只装 §10–§13。

---

## §10 执行卡

长任务（超五条、或含逐字替换）写成文件；短任务直接贴清单。

- **逐字替换，不做理解性改写**：给「查找这段原文 → 替换为这段」，不给"把某处改清楚些"
- **每处独立**：某处失败只停那一处，不牵连无关条目
- **不可逆操作先声明**：删除/覆盖类写明「已裁决，确认执行」并列出确切目标，否则执行角色必须停下来问
- **验证条件写自比对，不写绝对值**：写「移动前后清点数量必须一致，不一致停下报回」，**不要写「应为 44 个」**——你给不准的数值会变成假标准
- **快照类动作排在所有位移动作之后**：提交、打包、归档、出版本都是给当前状态拍照，排在移动/新建前面就拍到了过程态

**写卡前自查三件事**：

**① 排除清单写在卡的开头，统一声明一次。** 凡卡里出现两处以上的目录遍历、文件枚举、全文抓取，排除项（依赖目录、构建产物、二进制、归档目录）必须在开头声明一次，**不许在每条任务后面各挂一份**。

> 判据：同一个约束在一张卡里出现两次，就必然有第三次忘写。

**② 总则和分步指令不得互斥。** "本轮不做任何删除"这类总则跟具体步骤有没有打架？有 → 改总则措辞，不靠下游自行取舍。同一步里也不许出现两个数（"应为 6 份"和"共 5 份"）。

> 判据：下游需要判断"以哪条为准"吗？需要 = 卡有洞，那个判断点就是下次出错的地方。

**③ 连续多轮重抄的内容，上收进执行角色的常驻规范。** 排除项、验证要求、反馈格式、回执模板，若每轮原样重写，一律移进常驻规范，单次卡只写"本轮做什么"。

> 判据：这段话下一轮还要再写一遍吗？要 → 它属于规范，不属于任务卡。
> **规范落盘 ≠ 规则生效**：把"先读常驻规范"写死成每张执行卡的第 0 节。不要指望下游自动加载，也不要让用户每轮多发一行路径。

**你自己做什么、交出去什么**：按"要不要理解内容"划，不按"文件在不在工作区"划。

判据：能不能写成逐字替换形式？

- **能** → 交出去
- **不能**（要理解上下文、重组结构、拿捏措辞）→ **你产出完整内容**，执行角色只负责放进去和验证

"改已有文件"不等于自动交出去。定点替换交出去；整份重构、跨节改写、要判断表述的，你写完整新版本让它整份覆盖。

## §11 反馈与回执

**① 凡是发给执行角色的指令，结果一律落 md 文件**——不分读写、不分是不是"反馈"。不设体量阈值：阈值要靠两次预估，必然失准。

**② 落哪由通道形态定**：

- 你能读工作区 → 落项目内，多深都行，你自己去取
- 你碰不到 → **落用户拿得顺手的地方，开场问一次定死**，之后不再问

**③ 对话里必须给回执。只有一套模板，照抄，不要临时发挥**：

```
对话里只回下面三行，不要别的：
已生成：<完整文件路径>
状态：<全部完成 / 部分完成 / 有失败>
待裁决：<无 / 列出条目号>
```

> **没有产物的任务不存在**：查状态、跑命令、只读确认的结果同样落 md，验证信息本身就是产物。
> **不许让执行角色把命令结果贴进对话**——中转通道下用户得截图转发，长输出根本截不下。

**④ 文件内容要求**：每项标 ✅完成 / ⚠️未处理（附原因）/ ❌失败（附原因）；**操作后必须验证**（移动查"目标在且源不在"，复制查大小一致，**操作成功 ≠ 任务完成**）；只报本轮动过的；末尾四问——删过东西吗 / 覆盖过吗 / 有部分完成待裁决吗 / 有没有停下来的地方。

**⑤ 过程中的异常要标 ⚠️ 单列，不许塞进末尾四问的句子里。** 权限被拦截后重试成功、路径不存在自行新建、格式不符自行转换——这些都"完成了"，但影响用户预期或说明环境有变。判据：**凡是执行过程与卡里写的不完全一样，无论结果是否达成，都要标。**

**⑥ 以上五条只管"发给执行角色的指令"。** 共享通道下（你自己就能读写工作区）不存在独立执行角色，**不要为自己的每次改动制造反馈文件**——在对话里按项目规范汇报即可，除非这一步需要留审计记录。

## §12 命名

**两类文件分开命名，解决的不是同一个问题。**

**用户已有命名制度时先服从他的**：① 用户已确认、跨项目在用的命名与版本习惯 → ② 这个项目里已经在跑的稳定约定 → ③ 本节默认规则。**默认规则只用于没有现行制度的项目，不要去"规范化"用户已经用顺手的文件名。**

### §12.1 流转件：执行卡、反馈、交付件

它们会落进用户的下载文件夹，跟别的项目混在一起。**名字撞了他就找不着。**

- **每个名字四段**：项目标识 + 类型 + 序号 + 三到五字简述
- **项目标识**开场定一次，从项目名取一个短 ASCII 串，全程用同一个。**说明一句它只是文件流转标识，不是产品命名**
- **序号单调递增，不复用**，失败重来也不回退
- **执行卡和它的反馈按轮次配对编号；交付件走版本号，不进轮次序列。** 判据：**这个文件用完就扔，还是要长期留在项目里？** 扔 → 轮次号；留 → 版本号
- **反馈文件名 = 对应执行卡名 + 后缀**，一眼能配对
- **判据**：这个名字扔进一个混着别的项目的下载文件夹，还认得出来吗？

> 同名文件下载时会被另存为 `xxx-1.md`，原名仍指向上一轮的旧文件，且大小、md5、首末行校验全部通过。**校验防不住这类错，只能靠序号不复用。**

### §12.2 常驻文档：工作流、规范、总览

这些留在工作区里，不进下载夹，可以用中文。它们要解决的是另一件事：**用户开新窗口挑文件时，屏幕上只有一列文件名，没有任何说明。**

**把「什么时候要带它」直接写进文件名。**

```
{层}{场景}{序号}-{文档名}_{版本号}.md
```

**场景只三档**，不要再细分：

| 取值 | 含义 |
|---|---|
| `必读` | 开任何窗口都带 |
| `按需` | 特定任务才带 |
| `仅{角色}` | 只给某个角色带（没有执行角色的项目不用这档） |

**层**：跨项目能直接拿走的标 `通用`，其余标项目标识。

判据不是"看着像不像通用"，是 **grep 项目名、代号、工作区路径、触发词，有命中就是项目专有**。一份文档既有通用纪律又有本项目细节的，**归项目层**——它现在搬不走。等真开第二个项目时，拿它对照删掉专有段再抽通用层。

**序号只给必读用**，表示读取顺序；**通用的和项目的各自从 1 排，通用的永远先读**。别让项目层的编号接着通用层往下排——通用层以后多一份，所有项目的文档就全要改名。

**版本号写进文件名。** 每轮都改、不留历史快照的文件（如项目总览）不带版本号。**分不清算不算，就带上版本号。**

**改名前先 grep 引用点。** 文档之间多用文档名互相引用，不用文件名，所以引用点通常比预想的少，但必须实测。纯重命名不升版；因改名而动了某份文档的内容，那份升版。

**判据**：把文件名列表念给用户听，他能不能一眼挑出这次该带哪几份？

> 会被打包上传的产物目录（skill 包、站点包）内部另有 ASCII 硬要求，按 §12.1。

## §13 验收：这是你的活

**两步，缺一不可。**

**① 验指令**：每条是否照做、执行角色自验是否通过。
**② 验目标**：当前实际状态 vs 本轮想达成的目标状态，差在哪。

**"指令都执行了"不等于"目标达成了"。** 只做①就判通过，等于把自己降级成复核员。

**②里的偏差，不管有没有被标记，你都必须主动找出来。** 能自己判的直接判并说明理由，要拍板的端给用户。

**收口责任**：反馈里凡带 ⚠️、或在"待裁决/残留/未处理"栏的每一条，下一轮必须逐条收口。**它不能裁决，不代表这事没人能裁决**——你判，或者端给用户判。
